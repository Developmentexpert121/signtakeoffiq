## Session 5 — Multi-File Floor Plan Extraction

### The Core Problem
Walking Court has 9 floor plan PDFs uploaded. Result: 36 signs. Expected: ~300+.

Two root causes confirmed by reading the actual plans:

**1. Multi-file aggregation gap**
The pipeline processes floor plan files but may not be correctly aggregating rooms across all 9 uploaded files. Each file needs to be processed and rooms merged into a single inventory. The pipeline must iterate over ALL files in the floor_plan slot, not just the first or a subset.

**2. Floor replication not implemented**
AA103-A/B/C covers Levels 3-6 (4 identical floors). When `floorLabel = "Floors 3-6"`, the pipeline should extract rooms once from that sheet and replicate them 4 times with different level assignments. Currently each uploaded file is treated as exactly one floor regardless of the floor label content.

**3. Residential unit number extraction**
Walking Court floor plans label units as "SEE UNIT A A209", "SEE UNIT A A211" etc. The room identifier (A209, A211) is separate from the room type label ("SEE UNIT A"). The current Gemini vision prompt extracts "SEE UNIT A" as the room name and misses or drops the unit number. For residential buildings, the vision prompt needs to specifically look for unit numbers in this format and use them as the room identifier.

**4. Sign schedule image table extraction (AA831)**
The AA831 sheet has three dense image-based signage schedule tables listing every room number, room name, and sign text — estimated 300-400 entries covering all units across all floors. These are rasterized tables, not machine-readable text, so pdfplumber returns 0 rows. Fix: rasterize at higher DPI, crop to the table area, send cropped image to Gemini with a focused table-extraction prompt. This would give the architect's exact sign count without needing floor plan vision extraction at all for this building type.

### Session 5 Build Plan

**Priority 1 — Multi-file aggregation (pipeline.ts)**
Confirm the pipeline iterates over ALL files tagged `floor_plan` in the slot and merges extracted rooms. Add diagnostic logging showing how many rooms were extracted per file and the running total. If rooms from files 2-9 are being dropped, fix the aggregation loop.

**Priority 2 — Floor replication from floor label (pipeline.ts)**
In `parseLevelFromLabel()`, detect range patterns: "Floors 3-6", "Levels 3-6", "3rd-6th floor" etc. When a range is detected, return `{ levels: [3,4,5,6], replicate: true }`. In the room extraction step, when `replicate: true`, clone all extracted rooms once per level in the range with the correct level assignment. This means AA103 uploaded with label "Floors 3-6" produces 4× the rooms, each stamped with their correct floor.

**Priority 3 — Residential vision prompt update (pipeline.ts)**
For `buildingType = "residential"`, add specific instructions to the Gemini vision prompt: "For residential buildings, look for unit numbers in formats like 'A209', 'B301', 'Unit 101' even when they appear as small reference numbers near door locations. These are the room identifiers, not the room type label above them. Extract each unit number as a separate room."

**Priority 4 — Sign schedule image table extraction (pipeline.ts + sidecar)**
When a sign schedule sheet is processed in Step 3a and `extractTable` returns 0 rows (image-based table), trigger a fallback: rasterize at 300 DPI (higher than current 150 DPI), detect table region (large rectangular area in bottom-left of page), crop to that region, send to Gemini with prompt: "This is an architectural signage schedule table. Extract every row as JSON: { roomNumber, roomName, signText, quantity }. Include all rows — there may be 200-400 entries. Return JSON array only." Feed results into `signSchedule[]` accumulator as schedule-sourced rooms.

**Philosophy note:** Plans are all different. The goal is not to handle every edge case perfectly — it's to extract as much information as possible from whatever the user uploads, aggregate it correctly, and be transparent about what was found. Duplicate uploads are the user's responsibility. The pipeline should process every file in the slot independently and merge results.

## Architecture Notes
